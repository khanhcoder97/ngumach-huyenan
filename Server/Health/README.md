# Ngu Mach Huyen An — Health Server

Minimal ASP.NET Core API (net10.0) exposing the health check, the P1 authoritative movement slice, the QOD-03 combat, quest, inventory and teleport service skeletons, the QOD-13 quest-progress/interact slice, the QOD-14 turn-in/reward slice, and the QOD-18 equipment slice.

## Endpoints

| Method | Path | Purpose |
|---|---|---|
| GET | `/health` | Liveness check; unchanged from the P0 scaffold |
| POST | `/p1/sessions` | Create an in-memory player session on `MAP_BEN_MUA` |
| POST | `/p1/move` | Submit a `MoveIntent` envelope for the session in `X-Session-ID` |
| GET | `/p1/world/{sessionId}` | Read the latest authoritative `WorldSnapshot` |
| POST | `/p1/combat` | Submit a `CombatInput` envelope for the session in `X-Session-ID` |
| GET | `/p1/quests/{sessionId}` | Read the authoritative quest states for the session character |
| GET | `/p1/inventory/{sessionId}` | Read the authoritative `InventorySnapshot` for the session character |
| POST | `/p1/quests/accept` | Accept an `AVAILABLE` quest for the session in `X-Session-ID` (feature-flagged, off by default) |
| POST | `/p1/world/interact` | Claim an `INTERACTABLE` or gather from a `GATHER_NODE` world entity (feature-flagged, off by default) |
| POST | `/p1/quests/turnin` | Turn in a `READY_TO_TURN_IN` quest and receive atomic rewards (feature-flagged, off by default) |
| POST | `/p1/inventory/equip` | Move a `BAG` item to its catalogue slot (feature-flagged, off by default) |
| POST | `/p1/inventory/unequip` | Return an equipped item to the bag (feature-flagged, off by default) |
| GET | `/p1/inventory/v2/{sessionId}` | Read the twelve-slot `InventorySnapshotV2` view of the same inventory (mapped only with `P1:AlphaProfile:Enabled`) |
| POST | `/p1/inventory/v2/equip` | Move a `BAG` item to the slot its canonical catalogue label names, in the v2 vocabulary (`P1:AlphaProfile`) |
| POST | `/p1/inventory/v2/unequip` | Return the item worn in one of the twelve slots to the bag (`P1:AlphaProfile`) |
| POST | `/p1/v2/combat` | Submit a v2 `CombatInput` for the session (mapped only with `P1:CombatV2`) |
| GET | `/p1/v2/world/{sessionId}` | Read the AOI-filtered v2 snapshot: entities, self, and the boss/mob health policy (`P1:CombatV2`) |
| GET | `/p1/v2/events/{sessionId}` | Read the reliable v2 event stream from a cursor, with explicit resync codes (`P1:CombatV2`) |
| GET | `/p1/encounters/current` | Read the live encounter snapshot for this owner - boss hp/phase/life/revision and the in-flight move (`P1:AlphaProfile`) |
| GET | `/p1/encounters/{encounterId}` | Read one encounter by id; another owner's id answers `encounter_not_found` (`P1:AlphaProfile`) |
| POST | `/p1/actor/death-return` | Return a downed actor to the design anchor at the approved HP rule; the payload carries no coordinates (`P1:AlphaProfile` **and** `P1:DeathReturn`) |

Every response, including errors, carries `X-Correlation-ID`. A safe incoming value (1–64 characters of ASCII letters, digits, `-`, `_`, `.`) is echoed; otherwise a new GUID is generated.

## Run

```bash
dotnet run --project Server/Health/Health.csproj
```

The service listens on `http://localhost:5000` unless `ASPNETCORE_URLS` or launch settings override it.

The server loads `Implementation/Content/map_bounds.json` at startup by walking up from the working directory, content root and application base directory. Override with `Content__MapBoundsPath=/absolute/path/map_bounds.json` if needed. It likewise loads canonical `QuestDefinition` content from `Implementation/Content/Examples/QuestDefinition` (override with `Content__QuestsPath`), canonical combat skills from `Implementation/Content/Examples/SkillDefinition` (override with `Content__SkillsPath`), and the built world record catalog from `Implementation/Content/Runtime/world_records.json` (override with `Content__WorldRecordsPath`). Startup fails if the configured map is unknown, the spawn is outside bounds, the movement configuration is inconsistent, a quest or skill definition is invalid, or a quest objective target has no matching world record/NPC anchor.

```bash
dotnet build Server/Health/Health.csproj
```

## Move

The request body is a P1 `Envelope` whose payload is `MoveIntent`; the session ID travels in the `X-Session-ID` header.

```bash
curl -i -X POST http://localhost:5000/p1/move \
  -H "Content-Type: application/json" \
  -H "X-Session-ID: <SESSION_ID>" \
  -H "X-Correlation-ID: demo-move-1" \
  -d '{
    "schemaVersion": 1,
    "requestId": "11111111111111111111111111111111",
    "idempotencyKey": "22222222222222222222222222222222",
    "sentAtUtc": "2026-10-26T07:00:00Z",
    "characterId": "CHR_MINH_KIEM_01",
    "payload": { "inputSequence": 1, "moveX": 1, "moveY": 0 }
  }'
```

A successful move returns `200` with the updated snapshot and an incremented `revision`.

Replaying the same `inputSequence` returns `409` with `stale_sequence` and does not change position:

```json
{
  "schemaVersion": 1,
  "requestId": "11111111111111111111111111111111",
  "serverTimeUtc": "2026-10-26T07:00:01Z",
  "revision": 2,
  "error": {
    "code": "stale_sequence",
    "messageKey": "P1.ERROR.STALE_SEQUENCE",
    "retryable": false,
    "fieldErrors": ["payload.inputSequence"],
    "correlationId": "demo-move-1"
  }
}
```

## Combat

`POST /p1/combat` accepts a P1 `Envelope` whose payload is `CombatInput` and uses the same `X-Session-ID` header. Fields follow `Implementation/Contracts/P1/CombatInput.schema.json`; `inputSequence`, `skillId`, `aimX` and `aimY` are required, `targetId` is required for non-self skills.

```bash
curl -i -X POST http://localhost:5000/p1/combat \
  -H "Content-Type: application/json" \
  -H "X-Session-ID: <SESSION_ID>" \
  -H "X-Correlation-ID: demo-combat-1" \
  -d '{
    "schemaVersion": 1,
    "requestId": "33333333333333333333333333333333",
    "idempotencyKey": "44444444444444444444444444444444",
    "sentAtUtc": "2026-10-26T07:00:02Z",
    "characterId": "CHR_MINH_KIEM_01",
    "payload": {
      "inputSequence": 3,
      "skillId": "SK-MK-01",
      "aimX": 1,
      "aimY": 0
    }
  }'
```

A successful cast returns `200` with the schema-shaped `combat.effect` event, the session ID and the post-cast `revision`:

```json
{
  "schemaVersion": 1,
  "requestId": "33333333333333333333333333333333",
  "sessionId": "<SESSION_ID>",
  "serverTimeUtc": "2026-10-26T07:00:02Z",
  "revision": 4,
  "result": {
    "eventId": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "eventType": "combat.effect",
    "aggregateId": "CHR_MINH_KIEM_01",
    "aggregateRevision": 4,
    "emittedAtUtc": "2026-10-26T07:00:02Z",
    "schemaVersion": 1,
    "payload": {
      "sourceId": "CHR_MINH_KIEM_01",
      "targetId": "CHR_MINH_KIEM_01",
      "skillId": "SK-MK-01",
      "cooldownEndsAtUtc": "2026-10-26T07:00:12Z"
    }
  }
}
```

- `SK-MK-01` is `SELF`, so the caller is its own target and no world entity is needed. `SK-MK-02` without `targetId` returns `400 invalid_payload`; `SK-MK-02/03` with an unregistered target returns `404 target_not_found`. Damage, hit chance and death are intentionally absent until canonical stat/damage data and authoritative world targets exist.
- The server still owns results: `aimX`/`aimY` and `clientTimeUtc` are validated but never trusted for damage or hit resolution.
- **One input sequence per character.** `inputSequence` is shared with `/p1/move`; a combat cast advances `LastInputSequence` exactly like a move, so the client must keep a single strictly increasing counter across both endpoints. Reusing a sequence returns `409 stale_sequence`.
- Rejected casts do not consume the sequence and do not change `revision`, MP or position.

## Quest and inventory reads

Both are read-only projections for client UI. No accept/turn-in or add/remove command is exposed; those stay server-side seams.

```bash
curl -i http://localhost:5000/p1/quests/<SESSION_ID> \
  -H "X-Correlation-ID: demo-quests"

curl -i http://localhost:5000/p1/inventory/<SESSION_ID> \
  -H "X-Correlation-ID: demo-inventory"
```

`/p1/quests/{sessionId}` returns one `QuestState` per canonical `QuestDefinition`, using the state already validated by `QuestState.schema.json`:

```json
{
  "schemaVersion": 1,
  "requestId": "55555555555555555555555555555555",
  "sessionId": "<SESSION_ID>",
  "serverTimeUtc": "2026-10-26T07:00:03Z",
  "result": [
    {
      "questId": "P00-01",
      "state": "AVAILABLE",
      "stepId": "STEP_P00_01_PACKAGES",
      "objectiveCounters": { "OBJ_P00_01_PACKAGES": 0 },
      "revision": 1
    }
  ]
}
```

`/p1/inventory/{sessionId}` returns an `InventorySnapshot`. A session that has not been granted anything yet returns `inventoryRevision: 0` with empty `items` and `currencies`; the server does not seed starting gear.

Unknown session IDs return `404 session_not_found`. Reading quest state creates the row lazily so availability is refreshed; it never changes position, revision or resources of the world snapshot.

## Quest accept (feature-flagged)

`POST /p1/quests/accept` is mapped only when `P1:QuestAccept:Enabled=true`; otherwise the POST handler is not mapped and the request falls through to the `GET /p1/quests/{sessionId}` read route template, which answers `405`. It is **off by default** because the interaction line-of-sight guard has no walkability bundle yet — enabling it logs `DEV STUB: P1:QuestAccept is enabled...` at startup. Contract: `Implementation/Contracts/P1/QuestAcceptRequest.schema.json` + `QuestAcceptResponse.schema.json`; proposal and guard order in `Implementation/Work_Orders/Proposals/QOD-08_QuestAcceptRequest_vi.md`.

```bash
curl -i -X POST http://localhost:5000/p1/quests/accept \
  -H "Content-Type: application/json" \
  -H "X-Session-ID: <SESSION_ID>" \
  -H "X-Correlation-ID: demo-accept" \
  -d '{
    "schemaVersion": 1,
    "requestId": "55555555555555555555555555555555",
    "idempotencyKey": "99999999999999999999999999999999",
    "sentAtUtc": "2026-10-28T07:00:00Z",
    "characterId": "CHR_MINH_KIEM_01",
    "payload": { "questId": "P00-01", "npcId": "NPC_LYAN" }
  }'
```

Guards run in order: session → quest catalog → `npcId` = canonical `startNpcId` → same map/floor → foot distance ≤ `MaxInteractionDistanceWu` → prerequisites/level → `AVAILABLE`. Success flips the quest to `ACTIVE` exactly once and leaves position, HP/MP and the movement/combat `inputSequence` untouched. `idempotencyKey` is scoped to the character: replaying the same key with the same payload returns the first result; the same key with a different payload returns `409 idempotency_conflict`.

Line of sight is enforced from `MapTopology` bundles (`Implementation/Content/Examples/MapTopology`): a query must share `mapId`+`floorId`, stay inside walkable polygons, and not cross a blocked polygon from the actor foot to the NPC anchor. Only bundles with `reviewState: REVIEWED` are used; the shipped fixture is `SYNTHETIC_TEST_ONLY`, so the current server reports `not_enforced` and the endpoint keeps its DEV STUB warning. Bundle rules are documented in `Implementation/Work_Orders/Proposals/QOD-10_MapTopology_vi.md` and validated by `python Implementation/Tools/validate_topology.py`.

NPC anchors come from `Implementation/Content/Runtime/npc_anchors.json`, generated from the canonical spawn manifest:

```bash
python Implementation/Tools/build_npc_anchors.py
```

## Interact (feature-flagged)

`POST /p1/world/interact` is mapped only when `P1:Interact:Enabled=true`; otherwise the POST handler is not mapped and the request falls through to the `GET /p1/world/{sessionId}` read route template, which answers `405`. It is **off by default** because no reviewed walkability bundle exists yet — enabling it logs `DEV FIXTURE: P1:Interact is enabled...` at startup. Contract: `Implementation/Contracts/P1/InteractRequest.schema.json` + `InteractResponse.schema.json`; proposal and guard order in `Implementation/Work_Orders/Proposals/QOD-13_QuestProgressGathering_vi.md`.

```bash
curl -i -X POST http://localhost:5000/p1/world/interact \
  -H "Content-Type: application/json" \
  -H "X-Session-ID: <SESSION_ID>" \
  -H "X-Correlation-ID: demo-interact" \
  -d '{
    "schemaVersion": 1,
    "requestId": "66666666666666666666666666666666",
    "idempotencyKey": "77777777777777777777777777777777",
    "sentAtUtc": "2026-10-29T07:00:00Z",
    "characterId": "CHR_MINH_KIEM_01",
    "payload": { "targetId": "ENT_MAN_BM_OBJ_BM_PACKAGE_01" }

```

A successful claim returns `200` with an `InteractResult`: `interactionId` (hex32), `targetId`, `recordId` (the world record the entity resolved to), `kind` (`INTERACTABLE` or `GATHER_NODE`), `outcome` (`collected` or `gathered`), `targetState` (`DEPLETED` for shared interactables, `AVAILABLE` for per-character claims — gather nodes and the P00-01 packages), `claimedAtUtc`, optional `respawnAtUtc`, optional `yield` (`itemId` + `quantity` for gather nodes) and `questUpdates` — the changed `QuestState` rows from the server-owned `RecordVerifiedEvent` call:

```json
{
  "schemaVersion": 1,
  "requestId": "66666666666666666666666666666666",
  "sessionId": "<SESSION_ID>",
  "serverTimeUtc": "2026-10-29T07:00:00Z",
  "result": {
    "interactionId": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "targetId": "ENT_MAN_BM_OBJ_BM_PACKAGE_01",
    "recordId": "MAN-BM-OBJ_BM_PACKAGE_01",
    "kind": "INTERACTABLE",
    "outcome": "collected",
    "targetState": "AVAILABLE",
    "claimedAtUtc": "2026-10-29T07:00:00Z",
    "respawnAtUtc": "2026-10-29T07:00:20Z",
    "questUpdates": [
      {
        "questId": "P00-01",
        "state": "ACTIVE",
        "stepId": "STEP_P00_01_PACKAGES",
        "objectiveCounters": { "OBJ_P00_01_PACKAGES": 1 },
        "revision": 3
      }
    ]
  }
}
```

Guards run in order: idempotency replay (`idempotencyKey` scoped to the character; same key + same payload returns the stored result, same key + different payload → `409 idempotency_conflict`) → target exists in the world entity registry → kind is `INTERACTABLE` or `GATHER_NODE` → same map/floor → foot distance ≤ `MaxInteractionDistanceWu` (5) → line of sight (only with a `REVIEWED` topology bundle; otherwise `not_enforced`) → profession gate (`AssumedProfessionLevel` vs the record's `professionLevelRequired`; a DEV-fixture stand-in until character professions exist) → claim (`SHARED` interactables despawn the shared registry entry; `PER_CHARACTER` interactables and gather nodes use a per-character claim window in `GatherClaimStore`) → yield roll and inventory grant for gather nodes → `RecordVerifiedEvent` for quest progress. Rejected claims change no state and grant no items.

The `P00-01` packages (`ENT_MAN_BM_OBJ_BM_PACKAGE_01..03` at x=36/44/52) are the minimal acceptance slice: collecting all three flips the quest to `READY_TO_TURN_IN`. They carry `claimPolicy: PER_CHARACTER` in `world_entities_bm.json` (source: `Production_Rules_Complete_v1_vi.md` §5 — each package counts at most once per character and never removes the world item for other characters), so two characters can collect all three without waiting for a global respawn; the 20 s window is a **labelled DEV fixture**, not canonical balance. World records come from `Implementation/Content/Runtime/world_records.json` (352 records built by `python Implementation/Tools/build_world_records.py`); entity registries are rebuilt by `python Implementation/Tools/build_world_entities.py`, and CI verifies both files have no drift from their sources.

Failure codes: `invalid_payload` (400), `session_not_found` (404), `target_not_found` (404, retryable), `invalid_target` (400), `out_of_range` (422, retryable), `target_not_available` (409), `profession_level_insufficient` (422), `idempotency_conflict` (409).

## Combat internals (QOD-03/QOD-06)

`POST /p1/combat` exposes `ICombatService` for the self-targeting `SK-MK-01` path. The service stays the server-side seam for future `combat.input` work:

- `ICombatSkillCatalog` loads `SK-MK-01..03` from canonical `SkillDefinition` content (class, cooldown, MP cost, targeting type, range, angle, max targets, per-mode coefficients, telegraph and VFX key). No balance values are duplicated in C#.
- `ICombatTargetProvider` is a composite: the world-entity registry resolves alive mobs/bosses by entity instance ID (map/floor/position from canonical placements), plus an in-memory registry used by dev/test. Non-self skills still return `target_not_found` for dead, NPC or unregistered IDs.
- `InMemoryCombatService.Resolve(PlayerSession, CombatCommand)` validates the command, then applies gates in order: skill/class, per-actor `inputSequence`, target existence/map/alive/range, cooldown, and MP cost. Accepted casts decrement MP, advance `LastInputSequence` and `Revision`, and return a schema-shaped `combat.effect` `CombatEvent`. `LastInputSequence` is shared with movement, so clients must keep one monotonic input sequence per actor.
- Client `aimX`/`aimY` and `clientTimeUtc` are validated but not trusted. The canonical damage formula now exists as pure domain (`DamageFormula` + seeded `CombatRng`, QOD-16 phase 1) behind the `P1:CombatDamage` gate, but casts still return no `damage` or `hit`: nothing applies the formula until the QOD-16 proposal is approved.
- `combat.effect` is returned to the caller, not broadcast; transport and persistence arrive with the real-time layer.
- `idempotencyKey` is scoped to the character: replaying an accepted cast with the same key and payload returns the stored outcome before the stale-sequence guard; the same key with a different payload returns `409 idempotency_conflict`.

Internal failure codes: `unknown_skill`, `skill_not_available`, `invalid_target`, `target_not_found`, `target_not_alive`, `out_of_range`, `cooldown_active`, `insufficient_resource`, `unsupported_resource`, plus the shared `invalid_payload` and `stale_sequence`.

## Combat damage domain (QOD-16, phase 1)

The first QOD-16 slice lands the combat subset as internal domain only — no wire change and no damage applied until the proposal `Implementation/Work_Orders/Proposals/QOD-16_WorldProjectionCombatSubset_vi.md` is approved:

- `DamageFormula` implements Production Rules §2 exactly: hit roll `clamp(0.90 + accuracy − dodge, 0.05, 0.98)`, capped crit roll, `raw = (attack + flat) × coefficient × rankMultiplier × (1 + bonus)`, `mitigation = 100/(100 + max(0, armor))`, element `1 − clamp(resist, 0, 0.5 PvE / 0.3 PvP)`, crit ×1.5, DR cap 0.8, final `max(1, floor(...))`. The locked oracle holds: attack 20, coefficient 1.5, armor 10 → 27; crit → 40. `CombatRng` is seeded per `(castId, targetId, hitIndex)` with `combat-rng-v1` for reproducible audits.
- `Implementation/Tools/build_combat_mob_stats.py` deterministically exports `Implementation/Content/Runtime/combat_mob_stats_v1.json` from Art Bible §12 + Production Rules §4 (3 archetypes with the owner-locked `REFERENCE_L5` table, elite ×6/×1.6/×1.8, Mãng Cốt boss `BOSSDATA_BLOCKED` because `phaseGuard`/`interruptible` data does not exist yet). CI rebuilds the bundle and fails on drift.
- `SK-MK-03` range comes from the `combat.skillRangeMigrationWu` migration in `completion_v1.json` (4.4 WU) — the skill example intentionally has no `rangeWu`. Loaded only when the gate is on.
- `GuardPrecisionLoader` reads the owner-locked DEC-022 bundle (`Implementation/Content/DesignBaselines/p1_guard_precision_v1.json`, `DESIGN_ONLY_REQUIRES_RUNTIME_MIGRATION`) behind the same gate and validates window `[T, T+8)`, whiff `[T+8, T+28)`, counter-on-next-tick, 120°/4.4 WU cone, DR bucket cap and the 27/8/21/5 + counter 32/49 oracle arithmetic at load. `GuardTimeline` provides the pure window/cone/DR-bucket/deterministic-ordering helpers; `COUNTER_CONFIRMED` is a v2 event semantic (confirmation + one reserved counter, **not** counter damage).

**DEC-022 runtime (QOD-17, same gate).** `GuardWindowStore` keeps one window per character; `CombatTickEngine` opens it when `SK-MK-01` is accepted (cast-start tick and aim snapshot, baseline attack snapshot and the PvE coefficient 1.8) and resolves the reserved counter on the next tick. `GuardDefenseService` is the incoming side: a mob impact inside `[T,T+8)` from the front region (4.4 WU / 120°, inclusive edges, defender's current foot, cast-start facing) is reduced by 0.70 before the final floor, and the first valid front hit commits one confirmation per `guardCastId` — `COUNTER_CONFIRMED` in the session stream, `+2` Kiếm Ý capped at 5, one reserved counter. A lethal hit pays nothing: the window closes, resource drops to 0 and no counter exists. Natural expiry with no confirmation grants the whiff buff (0.20 DR for `[T+8,T+28)` on all incoming damage, never a confirmation) and the guard cast's `END` does not clear it. The counter re-runs every DEC-022 recheck at its own tick (both alive, same instance/floor, hostile, range, cone, LOS, invulnerability), rolls on its own seeded RNG channel `guardCastId|counter`, emits `IMPACT`/`MISS`/`CANCEL` against the confirmed source only (no retarget, no refund, no extra resource, no recursive counter, no boss hard control) and uses the same death/kill-credit path as a cast. Still unsupported: the guard window and `WHIFF_GUARD` are not snapshot status fields (a v2 contract proposal is required), player-vs-player counters cannot be exercised because no player-sourced hostile damage exists, and DoT/projectile/elemental sources have no content.

- `CombatEventStore` is the internal reliable event read for v2: typed events (`CAST_START`/`COUNTER_CONFIRMED`/`IMPACT`/`MISS`/`CANCEL`/`END`/`DEATH`), a monotonic per-session cursor starting at 1, a bounded per-session buffer (`P1:CombatEventStream`, DEV budget 512/page 200) and explicit resync instead of silent drops — readers behind the evicted range get `BUFFER_OVERFLOW`, stale cursors from a previous stream lifetime get `CURSOR_TOO_OLD`, both with no events (reconcile from the next snapshot). Appending the same `eventId` is a replay-safe no-op; reconnect cleanup is `RemoveSession`. Both v2 reads (`GET /p1/v2/world/{sessionId}`, `GET /p1/v2/events/{sessionId}`) are live behind `P1:CombatV2`, and the tick engine that writes these events is the same one QOD-17 shipped (guard window with its confirmation/whiff/counter, mob AI impacts, death and respawn).
- `WorldAoiProjectionService` is the v2 audience filter: internal candidates stay full-map, while each session receives MOB/BOSS/NPC/GATHER_NODE/INTERACTABLE only within the same map instance/floor/phase and AOI **enter 40 WU / leave 48 WU** (8 WU hysteresis), sourced from Online_Persistence_Release_Complete §2. NPCs project as `INVULNERABLE`/`targetable:false`/hp 0, the blocked boss as `BLOCKED` (never `DEAD`, not targetable), mobs with `REFERENCE_L5` hp and `ALIVE`/`DEAD` — **and a mob whose stats cannot be resolved as `BLOCKED`/`targetable:false`/hp 0**, which is what `P1:CombatDamage:Enabled=false` with the v2 and mob-behaviour gates ON produces: `CombatTickEngine.ResolveHit` skips any target whose max HP it cannot resolve, so a cast at it yields no `IMPACT`, no `MISS` and no death, and an `ALIVE`/`targetable:true` row at `hp: 0` advertised a fight the engine silently refuses to resolve (this was the integration thread's report on #96). The behaviour state (`IDLE`/`CHASE`/`TELEGRAPH` …) is unaffected because it is real data; only the health claim changes. A mob already `DEAD` in the registry stays `DEAD` rather than collapsing into `BLOCKED`. the alpha quest boss is the one exception and it is owner-scoped — through the optional `ICombatBossBridge` the *registered owner* of a live encounter sees `ALIVE`/`targetable:true` with the encounter's hp/maxHp (and `DEAD` with hp 0 once that encounter is defeated), while every other viewer keeps the `BLOCKED` policy, because `targetable` is derived from the same predicate the cast path uses, so the audience can never advertise a target the engine would refuse. Claimables expose only a per-caller `availability` (`AVAILABLE`/`COOLDOWN`, per-character claim windows, no quest flags). Reconnect cleanup is `RemoveSession`, which also forgets the hysteresis memory. CAM-TOPDOWN-WIDE-20261105 (`docs/production/TopDown_Wide_Camera_20261105_vi.md:11,13,35`) makes **64x36 WU** the default world view and 48x27 the compact option while forbidding any server-side change to match ("the staging build only changes the camera, not the server AOI, reveal, interaction/attack ranges, aggro or grants", and a competitive instance must run one profile for everyone rather than buy vision with a wider screen). That only stays true while the audience radius already covers the widest box a client can be configured with, so it is pinned arithmetically: the 64x36 corner is `sqrt(32^2 + 18^2) = 36.72` WU and the 48x27 corner is 27.54 WU, both inside the 40 WU enter radius, and the 48 WU leave ring sits outside the view box, so hysteresis can never drop an actor that is still on screen. Phase/instance stay labelled DEV placeholders (`OPEN_WORLD`, `#1`) **for the open world**: the Mãng Cốt encounter scopes its own actors per quest attempt rather than through these two constants, and the audience radius for that boss is owner-scoped (see `ICombatBossBridge` above).
- `CombatDamageFeature` gates everything: `P1:CombatDamage:Enabled=false` by default, and touching the bundle or migration while disabled throws. Enabling it logs a `DEV STUB` warning and changes no schema — but it does change values: with the gate OFF the audience reports every MOB as `BLOCKED`/`targetable:false`/hp 0 (see above), and `/p1/v2/combat` still answers `200` for a cast at such a mob because acceptance never checks the target's stats; it simply resolves nothing for it. Clients should read `targetable` on the snapshot row, not the cast status code, to decide whether a swing can land.
- `WorldEntityProjectionService` is the internal entity read-model (entityId, kind, map, floor, x, y, state, revision, lifeId, hp/maxHp): NPCs stay invulnerable with hp 0 (Art Bible §13), bosses stay hp 0 while `BOSSDATA_BLOCKED`, mobs use the `REFERENCE_L5` archetype stats (elite suffix applies the elite multipliers), and `lifeId` bumps on respawn. It is not yet wired into the world snapshot.

## Quest skeleton (QOD-03)

`GET /p1/quests/{sessionId}` exposes the state list read-only. No accept/turn-in command is exposed yet; `IQuestService` remains the server-side seam for those:

- `IQuestCatalog` loads canonical `QuestDefinition` files (currently `P00-01`) from `Implementation/Content/Examples/QuestDefinition`; unknown quest IDs are rejected.
- `InMemoryQuestService` keeps per-character state behind `IQuestStateStore` and supports `GetState`, `GetStates`, `Accept`, `RecordVerifiedEvent`, `TurnIn` and `Fail`.
- Allowed transitions: `LOCKED → AVAILABLE` when all prerequisites are `COMPLETED`, `AVAILABLE → ACTIVE` on accept, `ACTIVE → READY_TO_TURN_IN` when every canonical objective counter reaches its count, `READY_TO_TURN_IN → COMPLETED` on turn-in, and `ACTIVE`/`READY_TO_TURN_IN → FAILED` on failure.
- Objective progress is clamped to the canonical objective count and updates `revision`; invalid transitions return the current snapshot with `invalid_transition`. State rows are created lazily on first query/accept, and prerequisite availability is refreshed lazily on read.
- `RecordVerifiedEvent(actor, eventId, eventType, recordId, mapId)` is the only progress path: server-verified gameplay events (interact/gather claims, talks, kills) advance objective counters. Each event contributes **once**: `COLLECT`/`INTERACT`/`TALK` objectives are keyed by distinct `recordId` (`R:{recordId}`), `KILL` objectives by event (`E:{eventId}`). No event can double-count the same record, and events on another map never contribute. It is an internal seam for server-side events, not raw client input.
- Startup validation rejects quests whose `COLLECT`/`INTERACT` objective targets resolve to no world record on the objective's map, or whose `TALK` targets have no NPC anchor (`QuestCatalogValidator`); dangling IDs fail the boot instead of silently blocking progress.
- Canonical `QuestDefinition` has no step graph, so the initial `stepId` is derived from the first objective (`OBJ_…` → `STEP_…`); `P00-01` yields `STEP_P00_01_PACKAGES`.
- Rewards, XP, currency and items are not granted. Level-band eligibility is not enforced because `PlayerSession` has no level field yet.
- Internal failure codes: `unknown_quest`, `quest_not_found`, `invalid_transition`, plus the shared `invalid_payload`.

## Movement rules

- The server owns position. Client coordinates are never accepted; only a direction from `MoveIntent` is used.
- Direction is normalized, so diagonal input does not grant extra speed.
- Distance is `MoveSpeedWuPerSecond × elapsed server time`, with elapsed clamped to `MaxStepSeconds`. Client timestamps are validated for shape but never trusted for movement.
- The result is clamped to the canonical map bounds. Repeated movement into an edge stops at the edge rather than erroring.
- When a `REVIEWED` topology bundle exists for the map, the whole swept step is validated: the segment (with `ActorFootprintRadiusWu` clearance against blocked geometry) must stay inside walkable polygons and must not cross a blocked polygon. A blocked sweep returns `422 movement_blocked` without consuming the sequence, revision or position. Without a reviewed bundle the query reports `not_enforced` and movement keeps the P1 bounds-only behaviour (dev stub).
- `inputSequence` must strictly increase. A stale or repeated sequence is rejected before any state changes.
- `characterId` in the envelope must match the session.
- `idempotencyKey` is validated but movement is not deduplicated in P1; the monotonic sequence is the replay guard. Economic actions will add idempotency records later.
- `serverTick` is derived from a monotonic process clock at the canonical 20 ticks/second.

## Inventory skeleton

`IInventoryService` owns the authoritative per-character inventory. It is exposed read-only through `GET /p1/inventory/{sessionId}`; `Apply` stays a server-side seam, and the only HTTP mutations are the gated equip/unequip pair below (v1) and the `P1:AlphaProfile` v2 pair (see the v2 section). `GetSnapshot` returns a payload shaped like `Implementation/Contracts/P1/InventorySnapshot.schema.json`.
- **v2 inventory contract (QOD-21 Q3, now served behind `P1:AlphaProfile`):** `InventorySnapshotV2`, `EquipV2Request`, `UnequipV2Request` and `InventoryV2Response` (schemas + examples under `Implementation/Contracts/P1/`) state the approved side-by-side read model — twelve closed slots in design order (`slots` always lists all twelve, an empty slot carries `item: null`), `bagSlots: 100`, `slotSpec` = `V2_SIDE_BY_SIDE_KEEP_V1_FIVE_SLOT_CONTRACT`, and an `unsupported[]` that reports any equipped item the twelve cannot name (`UNMAPPED_SLOT`) instead of dropping it. The v2 slot vocabulary is implemented once in `InventoryV2Slots` (tokens, canonical CSV label map, collapse onto v1's five tokens) and the alpha validator checks the design list against it at startup, so the design and the code cannot drift apart; `LEGS` and `GLOVES` deliberately collapse to nothing because v1 never had tokens for them. The three `…/v2/…` routes are mapped when `P1:AlphaProfile:Enabled=true` and answer **404 with nothing registered** while it is off (the shipped default); behavior is documented under "v2 inventory surface" below.

`Apply(session, InventoryMutation)` is a single all-or-nothing transaction:

- Validation runs before any state changes. Character, template, instance, location, slot and currency identifiers follow the P1 patterns.
- `expectedRevision` is optional. If present and stale, the call returns `revision_conflict` with `retryable = true` and the current snapshot. Otherwise the inventory revision increments exactly once.
- Grants always create a new `ITM_<32 uppercase hex>` instance; the catalogue's `stack_limit` is not used for automatic stack merging yet.
- Removals address `instanceId`. An unknown instance returns `item_not_found`, over-removal returns `insufficient_items`, and the item version increments whenever its stack changes.
- Moves address `instanceId` with the location the caller expects to find (`fromLocation`) and the destination; a mismatch returns `wrong_location`, so a stale plan cannot relocate an item another transaction already moved.
- `EQUIPPED` slots must be unique. A taken slot returns `slot_occupied`.
- Currency deltas are aggregated; a negative resulting balance returns `insufficient_currency`, and zero balances are omitted from snapshots.
- Durability is caller-supplied, **and a grant that does not name one takes the canonical catalog's own value**: `ItemCatalogEntry.Durability` loads the `durability` column of `docs/production/Item_Master_Catalog_vi.csv` / `Item_Rarity_Variant_Catalog_vi.csv`, and `InMemoryInventoryService` resolves `ItemGrant.Durability` (now nullable, so "unspecified" is distinguishable from an explicit `0`) from it. A **blank cell is null, not 0** — every blank row in both catalogs is a consumable, and 0 is a value an item can legitimately carry, so reading a missing cell as 0 would say "broken" where the source says nothing. A template the catalog does not know still lands on 0 because there is no source to read, never because a default was invented. Audit answer for the reward coat (`EQ-MK-CHEST-T1-R-COMMON`, #87 23:58): its serialized `durability: 0` was **an uninitialized grant field, not intended non-durable metadata** — the catalog states 100 for it, as for **every** equipment row in both files (2100 variant rows and 420 master rows all carry 100; the 132 blank cells in each file are all non-equipment), so it now serializes 100. No durability rule beyond "the catalog carries it" exists in the sources, so nothing degrades or breaks at 0 yet, and no numeric default was introduced anywhere.

State is in memory and there is no seed inventory; a new character starts with no items and no currency.

## Equipment (feature-flagged)

`POST /p1/inventory/equip` and `POST /p1/inventory/unequip` are mapped only when `P1:Equipment:Enabled=true`; **off by default**. Contracts: `EquipRequest.schema.json`, `UnequipRequest.schema.json` and `EquipmentResponse.schema.json` (the result is the same `InventorySnapshot` the read route returns); the packet and the four owner answers are in `Implementation/Work_Orders/Proposals/QOD-18_Equipment_Contract_vi.md`.

Equipping is metadata-only: it moves one instance from `BAG` to `EQUIPPED` in the slot token derived from the catalogue, and unequip moves it back to `BAG`. No stat reaches combat, because Production_Rules §2 / DEC-023 do not define how `weapon_power`, `armor` and primary stats enter `DamageFormula` yet.

- The item catalogue merges `Item_Master_Catalog_vi.csv` and `Item_Rarity_Variant_Catalog_vi.csv`; the rarity variants are the ids quests actually grant (`EQ-MK-BOOTS-T1-R-COMMON`), so a handler that only knew the base catalogue would refuse the first real reward. Any equipment label with no approved wire token fails startup, except the two sourced labels the five-token enum cannot express (`Quần`, `Găng`), which stay in the catalogue and answer `not_equippable`.
- Claimed slot tokens are `HAT`, `CHEST`, `BOOTS`, `WEAPON`, `ACCESSORY`. `Character_Equipment_Inventory_Spec_vi.md` §3 defines **twelve** player slots, so v1 folds the six accessory labels into one `ACCESSORY` slot (only one accessory can be worn at a time until the slot contract is extended) and refuses `Quần`/`Găng`. Extending the enum is a contract change, not a server choice.
- Equip accepts only a `BAG` item with stack 1. A wrong `class_id` is `class_restricted`, a `required_level` above `PlayerSession.Level` is `level_required`, and a template the catalogue does not know or cannot map is `not_equippable`.
- No auto-swap: a taken slot returns `slot_occupied`, and the client must unequip first.
- `expectedRevision` is required and must equal the current inventory revision; otherwise `revision_conflict` (retryable) with the current snapshot. A successful call increments the revision exactly once.
- `idempotencyKey` is scoped to the character: a replay returns the recorded snapshot without moving anything again, and the same key with a different payload is `idempotency_conflict`. The ledger is in-memory, bounded to 256 entries and lost on restart.
- Equip/unequip do not touch quests, XP, loot or durability.
- Work order 29 states "Equipment metadata không được báo là effective stats", and that is now pinned twice instead of only promised in prose. `equipment.gear_stat_labels_have_no_wire_field` walks every public type in `Server.Health.Contracts` and fails if any property is named `WeaponPower`, `WeaponAttack`, `Armor`, `PrimaryStat`/`PrimaryValue`, `SecondaryStat`/`SecondaryValue`, `Strength`, `Vitality`, `FlatMaxHp`/`FlatMaxMp`, `HpMax`/`MpMax`, `PhysicalAttack`, `Attack`, `Defense` or `EffectiveStats` - the aggregation's own vocabulary, so the day somebody surfaces a derived number on a snapshot it names the type instead of quietly shipping it. Live actor numbers (`Hp`/`MaxHp`/`Mp`/`MaxMp`) are deliberately *not* in that list; the claim is that catalogue metadata has no wire home, not that stats are unspeakable. `equipment.wearing_the_hat_moves_no_actor_stat` is the runtime half: the DEC-023 aggregation prices the T1 hat at `HpMax == 212` against the 198 no-gear oracle, the hat is then granted and equipped for real, and the actor's four numbers stay exactly `(100, 100, 50, 50)` while the item flips to `EQUIPPED` - so "accepted equip moves only the inventory" is measured on both sides (the number exists in the read model, and the number does not reach the actor). The same check also re-reads the source cell: the master catalog states durability `100` for `EQ-MK-HAT-T1`, which is what an unnamed grant takes (the `7` in the earlier grant check is an *explicit* value winning, not the catalog - an earlier README line said otherwise and is corrected here).

### v2 inventory surface (`P1:AlphaProfile`, QOD-21 Q3)

`EquipmentV2Service` serves the approved twelve-slot vocabulary (`DESIGN-BM-Q3-20261104 inventory`, `slotSpec = V2_SIDE_BY_SIDE_KEEP_V1_FIVE_SLOT_CONTRACT`) over three routes mapped **only** while `P1:AlphaProfile:Enabled=true` — `GET /p1/inventory/v2/{sessionId}`, `POST /p1/inventory/v2/equip`, `POST /p1/inventory/v2/unequip`. With the gate off nothing is registered, so the read route 404s on its own template and the POSTs 404 rather than matching a GET template. This surface needs no `P1:Equipment` flag: the alpha profile is what authorises it.

- **One store, one revision.** v2 reads and writes the same `IInventoryService` state as v1, so `inventoryRevision` is the same aggregate counter in both views; a v2 equip bumps it exactly once, and a v1 request that expected the older value gets `revision_conflict`. The five-token `EquipmentSlots` enum, the v1 routes and the v1 payload shape are untouched — `GET /p1/inventory/{sessionId}` returns the identical `InventorySnapshot` and its schema gains no field.
- **The slot is never taken from the request.** Equip accepts an `itemInstanceId` only; the slot comes from `ItemCatalogEntry.SlotLabel` resolved through `InventoryV2Slots.TryResolveEntry`, so a client cannot place an item where the source does not name it. Unequip takes a `slotId` from the twelve (anything else is `invalid_payload` on `payload.slotId` before the ledger is consulted).
- **Two accessories, and the slots v1 cannot name.** The store keeps a second internal column, `InventoryItemEntry.SlotV2`, alongside the v1-collapsed `Slot`; occupancy is counted over `SlotV2 ?? Slot`. That is what lets a necklace (`NECK`) and a left ring (`RING_L`) be worn at once, which v1 forbids inside its single `ACCESSORY`. A piece whose v1 collapse is empty — `LEGS`, `GLOVES` — is written with `Slot = null`, so v1 reports the item as equipped with no slot token instead of inventing one. The asymmetry is deliberate and left unfrozen-by-v2: v1 still enforces "one item in `ACCESSORY`" over its own token, because tightening that would change the frozen v1 contract.
- **Rules shared with v1 on purpose:** `BAG`-only source with stack 1, `class_restricted` on a mismatched `class_id`, `level_required` on `required_level > PlayerSession.Level`, `slot_occupied` with no auto-swap, required `expectedRevision`, and a per-character `idempotencyKey` ledger (bounded to 256, replay returns the recorded snapshot without a second move, same key + different payload is `idempotency_conflict`).
- **Answers:** `200` with the full v2 snapshot on accept; `404 item_not_found` for an id the bag never held, `409 wrong_location` for an id already worn (or an empty slot on unequip), `409 revision_conflict` (retryable, carrying the current v2 snapshot), `409 slot_occupied` / `idempotency_conflict`, `422 not_equippable` for a potion or an equipment label outside the twelve, `422 class_restricted` / `level_required`, `400 invalid_payload` with the offending field names, `413` for an oversized body. An unknown or mismatched session is `404 session_not_found` / `400 invalid_payload ["characterId"]` like v1.
- **`unsupported[]` is never silent.** A worn item that neither the catalogue label nor either vocabulary can name — or a second item claiming one slot, which would be a store fault — is reported as `{instanceId, templateId, sourceSlot, reason: "UNMAPPED_SLOT"}` and stays out of `slots`/`bag` rather than disappearing. The self-check drives it through the store seam (a `POT-HP-01` granted into `EQUIPPED` slot `TOTEM`), because no route can write such a row.
- **Envelope:** `schemaVersion` must be exactly `2`; `P1Json` still rejects unknown members, so a v1 client cannot accidentally post a v2 body or a v2 body drift into fields the contract does not carry.
- **Finding (v1 wire widened in this checkpoint):** the canonical catalogue ships template ids with underscores (`EQ-MK-RING_L-T1-R-COMMON`) and the v2 item pattern already allowed `[A-Z0-9_]`, but the **v1** `templateId` pattern `^[A-Z0-9]+(?:-[A-Z0-9]+)*$` — in `InventoryValidation` plus `InventorySnapshot.schema.json`, `EquipmentResponse.schema.json`, `InteractResponse.itemId` and `TurnInResponse.templateId` — rejected them, so the v1 equip path would have failed validation on the first real quest reward carrying such an id (the self-check found it by seeding the twelve-slot fixtures). Those patterns gained `_` in their character classes (`^[A-Z0-9_]+(?:-[A-Z0-9_]+)*$`, and `^[A-Z][A-Z0-9_-]+$` for `InteractResponse.itemId`), matching the server validator's own pattern. This accepts strictly more than before and changes no field, enum or rule; it is called out because it touches the frozen v1 wire documents.

That is the source for Q5's shop/forge and Q7's guild/arena: the tokens now exist in the server's data, and none of them has a route.

## Consumables (domain only, no route)

Work order 29 Q5 names "consumable" and "HP/MP clamp". `Server/Health/Gameplay/Inventory/ConsumableCatalog.cs` reads the fourteen `Tiêu hao` rows of `Item_Master_Catalog_vi.csv` through the already-loaded item catalogue and classifies every one of them: seven state a percentage of a maximum (`POT-HP-01/02/03` = 25/35/45% HP, `POT-MP-01/02/03` = 20/30/40% MP, `POT-REVIVE-01` = 15% HP) and seven state an effect this server has no subsystem for (cleanse, durability repair, a teleport cast, three timed foods, a one-use protection). Refusals keep the source's own `primary_stat`/`primary_value` cells verbatim, so `effect_unsupported` can name the row instead of a generic no.

`ConsumableService.Consume(actor, itemInstanceId, expectedRevision, idempotencyKey)` is the transaction shape the rest of the inventory already uses: revision stated and compared first (`revision_conflict`, retryable), item must be in `BAG` (`wrong_location`), template must be a consumable (`not_consumable`), the catalogue's own `required_level` applies (`level_required`), and the restore is clamped so it can only move a pool **up** and never past its maximum (Production_Rules §2 rule 6). Exactly one stack unit is spent per accepted call, the idempotency ledger is per-character and bounded at 256 with a request hash so a same-key-different-payload retry is `idempotency_conflict`, and the mutation commits under the actor lock. The revive row is **not** treated as a free heal: it is framed as `Hồi sinh` in the source, and no sourced revive rule exists here, so it answers `revive_not_modelled`.

Two choices are recorded rather than invented. Rounding: the ruleset floors magnitudes (damage `floor`, XP `floor`) while the approved death-return rule ceils, and nothing speaks about healing - this floors, which makes `101 * 25% = 25,25 -> 25` and `3 * 25% = 0,75 -> 0`. And a drink with nothing to restore is **refused** (`no_effect`) instead of spending the item, because no source says a player loses a potion for drinking at full HP. Both are owner questions in `Implementation/Work_Orders/Proposals/QOD-24_Consumable_Use_Contract_Packet_20261105_vi.md` (Q1, Q2), together with the proposed route, gate and the four new error codes - which is why there is no endpoint: adding a `P1ErrorCodes` entry is a wire change.

## Teleport skeleton

`ITeleportService.Teleport(session, TeleportCommand)` is the authoritative teleport path. It is registered in DI but is not exposed over HTTP yet. The command is shaped like `Implementation/Contracts/P1/TeleportRequest.schema.json`.

- `mapId` must match `^MAP_[A-Z0-9_]+$` and exist in `map_bounds.json`; an unknown map returns `invalid_map`.
- Coordinates must be finite and inside that map's bounds. Teleport does not clamp; outside bounds returns `out_of_bounds`.
- `reason` must be one of `QUEST`, `DEATH_RETURN`, `CITY_RETURN`, `ADMIN`. `DEATH_RETURN` requires `hp <= 0`; every other reason requires `hp > 0`, otherwise `invalid_condition`.
- On success the session map, position and revision are updated under the session lock, and `LastMoveAtUtc` is reset so elapsed time before the teleport cannot be spent as movement.
- Teleport does not revive, heal or reset the movement sequence; respawn and death behavior stay in separate services.

Service `IQuestTurnInService` orchestrates an atomic transaction under the session lock:

1. **Idempotency** — `(characterId, idempotencyKey)` scoped like accept. Replay returns the first outcome; a different payload under the same key returns `409 idempotency_conflict`.
2. **Validate** — catalog → `npcId == turnInNpcId` → same map/floor → distance ≤ 5 WU → LOS (not enforced without REVIEWED topology) → state `READY_TO_TURN_IN`.
3. **Grant** — `IInventoryService.Apply` with canonical `rewards.currency` and `rewards.itemIds` (stack 1, `BAG`). All-or-nothing; failure aborts with no partial reward.
4. **Flip** — `IQuestService.TurnIn` transitions to `COMPLETED` (+1 revision).
5. **Ledger** — `RewardLedgerStore` records `(characterId, questId)` for reward-once audit.

Rewards use canonical data from the `QuestDefinition.rewards` block. XP is echoed with `applied: false` (no XP system yet). `unlocks` lists quest IDs enabled by the completion; their state refreshes lazily. The ledger is in-memory (lost on restart) and labelled as a dev fixture.

## V2 opt-in surface (QOD-16 phase 2)

`P1:CombatV2:Enabled=true` maps three prototype routes; with the gate off they are not mapped (requests fall through to the v1 routes or `404`). v1 messages and gates are unchanged. Impact and damage are **not** tied to this gate: they need the separate `P1:CombatDamage` switch, so `P1:CombatV2` ON with the damage gate OFF maps the routes, serves audience rows as `BLOCKED`/hp 0 and resolves a cast into no event naming that target - the exact shape issue #96 was filed against, now pinned by the `audience-gateoff` e2e profile and by `aoi.mob_blocked_when_damage_gate_off`.

- `GET /p1/v2/world/{sessionId}` returns the audience snapshot (`WorldSnapshotV2`): `schemaVersion: 2`, `mapInstanceId`/`floorId`/`phase`, `audience { aoiEnterWu: 40, aoiLeaveWu: 48 }`, `self` (hp drops when a mob impact lands, and `revision` moves with it) and the AOI-filtered entity read model (NPC `INVULNERABLE`, blocked boss `BLOCKED` — or, for the owner of a live alpha encounter only, the encounter's `ALIVE`/`targetable`/hp view and `DEAD` once defeated — mobs with `REFERENCE_L5` hp whose `state` is the AI lifecycle `IDLE`/`AGGRO`/`CHASE`/`TELEGRAPH`/`ATTACK`/`RECOVER`/`RETURN`/`DEAD`, per-caller node `availability`).
- `POST /p1/v2/combat` accepts `BASIC_ATTACK | SKILL` (v2 envelope, `schemaVersion: 2`) and returns `castId`, `mp`/`mpCost`, `cooldownEndUtc`, `nextInputSequence` and **only the events that already occurred** (`CAST_START`); future impacts are read through the event cursor. Basic attack is Minh Kiếm-only (P1 subset), costs no MP and has a 0.25 s recovery cooldown; skills reuse the v1 guards (class, sequence, cooldown, MP) and idempotency replays return the same cast without a new event.
- `GET /p1/v2/events/{sessionId}?cursor=N&max=M` returns `{ nextCursor, resyncRequired, resyncReason?, events }` from the bounded per-session stream; stale cursors report `CURSOR_TOO_OLD`, evicted ranges `BUFFER_OVERFLOW`, and reconciliation is silent (no audio/VFX replay).
- Responses reuse the v1 error envelope (`error.code` values stay in `CombatErrorCodes`), and a successful v2 combat response carries `schemaVersion: 2`.
- **Tick resolution (QOD-17 core):** accepted v2 casts are scheduled on the 20 Hz `CombatTickEngine` (`WorldTickBackgroundService`). A basic attack lands one impact on tick +3 (windup 0.15 s) with coefficient 1.0; `SK-MK-03` lands its three authored hits on ticks +2/+5/+8 with coefficients 0.45/0.55/0.90 against up to 5 targets in the 4.4 WU/100° cone; `SK-MK-01` opens a DEC-022 guard window whose counter resolves on the following tick, and `SK-MK-02` resolves its swept movement on tick +7 (prep 0,15s + dash 0,20s at 20 Hz): the actor walks the ray with the accepted facing, stops flush before a blocker or the map edge, and never moves when the sweep is blocked at the start. Damages use the labelled completion_v1 baseline (attack 20, armor 10, accuracy 0.0025, crit 0.0525) plus the `REFERENCE_L5` mob defense through `DamageFormula` — the basic oracle is 19 against CARPLING (4.2 armor) and MK03 is 8/10/17. Mob HP is life-scoped (`MobCombatStateStore`), a death is emitted once per `lifeId`, the killer (last HP-damage source, DEV policy) receives the KILL quest event keyed by the death event id, and respawn bumps `lifeId` with fresh HP. Impact re-checks alive target, same `lifeId`, instance/floor, range, cone and **line of sight** at the scheduled tick (only a `REVIEWED` topology bundle can block; the shipped synthetic bundle answers `NotEnforced`), and a cast whose actor died or changed map/floor is cancelled once with `CANCEL` + `END` before any damage or kill credit. Misses emit `MISS` with no damage. A cached command replay is returned as `Replayed` and the endpoint must not schedule it again, so a retry after `END` cannot add a second `END`, hit, death, kill credit or guard window. Remaining QOD-17 work is exposing guard/whiff status in the v2 snapshot (contract proposal) plus the XP and loot grant paths.

- **Loot recipes (QOD-17, dry-run):** `python Implementation/Tools/build_loot_recipe.py` exports the canonical `Loot_Recipe_Reward_Production_Data_vi.csv` (57 sources / 184 entries) into `Implementation/Content/Runtime/loot_recipe_v1.json` with `grantEnabled: false` and `grantBlockedReason: COIN_BAND_MISSING`. **That remains the shipped default.** `DESIGN-BM-Q3-20261104 loot` adds one opt-in path: `P1:AlphaLoot:GrantEnabled` (default `false` in `appsettings.json`) pays a kill only when `P1:AlphaProfile:Enabled` is also on and the design is explicitly private alpha (`APPROVED_FOR_IMPLEMENTATION_PRIVATE_ALPHA_NOT_PLAYTEST_BALANCED`, `defaultEnabled: false`) — asking for the payout flag without the profile is a startup failure, not a silent no. With the profile on and the flag off, each death is recorded as `DRY_RUN_NON_PAYABLE` (not "no source"), and because that answer is recorded under the same death key, turning the flag on later cannot back-fill the earlier deaths. A grant pays the sourced coin band (`mobLevel..2*mobLevel`, inclusive, uniform over the band drawn from the same deterministic roll as the recipe) plus the recipe's `SELECT_ONE` items, in one inventory mutation, keyed by the design's `[profileVersion, characterId, deathEventId, lifeId, groupId]` so a retry returns the same receipt instead of re-rolling. The runtime rolls once per group (`1200` bps for ordinary pools) and then `SELECT_ONE` by weight using the versioned `loot-rng-v1` server RNG; the same kill key reproduces the same receipt, the ledger dedupes retries, and the P1 mob→source mapping is explicit (`MOB_CARPLING`→`LT_MOB_CARPLING`, elite and boss pools included, boss flagged blocked). Receipts are dry-run only — no item/currency is granted until the coin-band reward bundle exists and is reviewed.

## Headless E2E scenario (QOD-15)

Two invariants the alpha escort leg learned the hard way (work order 30 item 2, fixed in `2f2bf9a` and verified green at `835ae2a`), because both look like test noise and neither is:

- **A world row that is present and `DEAD` is a witnessed death; a row that is absent is not.** The escort loop used to test `state == "DEAD"` and `continue` without crediting it, so a member that died while the loop was working on another target could never be counted and the leg failed as `witnessed 2 of 3 deaths` while all three rows reported `('DEAD','DEAD',False,0)`. Absence stays uncounted because the manifest group respawn makes it ambiguous - that is the rule's original purpose.
- **A fight is bounded by the fight, not by the clock.** `alpha_kill` keeps casting while the target's HP is moving, gives up after 60 casts with no HP movement, and ceilings at `maxHp + 200` casts. The previous shape (fixed 1200 iterations plus a wall-clock sleep) let a slower server fail a leg: the per-impact logging in `5c77b8f` starved the boss to 57 of the ~67 casts it needed against 1200 HP and CI went red for that reason alone. Reverted in `3d16072`, re-landed in `835ae2a` once the bound was arithmetic: the chain then measured 112 checks with 268 impacts logged.

`alpha_ensure_alive` (`c324df6`, CI 25/25) additionally revives a downed actor over `POST /p1/actor/death-return` before each kill batch - the actor dying mid-chain (`IMPACT B:DOWN phase 3 bossHp 244 damage 32 (12 -> 0)`) was the real cause of the "the quest boss never died, 57 casts accepted" failure, and the revival goes through the same public route a client would use rather than a private grant. Residual: no run has driven HP to 0 with the revival present, so that branch is still unexercised even though the route has its own 17-check profile.

Each route answers one of three ways and the profile distinguishes them: the unmapped status (`405` where the path still matches a GET read template, `404` where it matches nothing), a mapped handler refusing the deliberately empty body with `400`, and the mapped-encounter `404` carrying `{"error":{"code":"encounter_not_found"}}` — the only way to tell `/p1/encounters/current` apart from an unmapped path on the wire. The table is a literal, so a leg's 18 checks never depend on server state, and an empty leg (`CombatDamage`, `MobBehavior`, `DeathReturn` alone, `QuestTalk` alone, `Portal` alone) is what stops a future edit quietly attaching a route to a gate that must not own one. `DeathReturnAlpha` is the pairing proof: `/p1/actor/death-return` is mapped only when `P1:AlphaProfile` **and** `P1:DeathReturn` are both on, which is the shape DEC-DEATH-RETURN-20261105 freezes; the single-gate `DeathReturn` leg must therefore see the bare 404. **`QuestTalkAlpha` is the second pairing case and `QuestTalk` alone is its negative:** `/p1/quests/talk` answers `405` with only its own switch on (the path still matches the `GET /p1/quests/{sessionId}` template, and no handler is mapped) and `400 invalid_payload` once `P1:AlphaProfile` joins it. **`PortalAlpha`/`Portal` is the third pair, measured the same way** (`/p1/world/portal` matches the `GET /p1/world/{sessionId}` template, so unmapped is `405`, mapped is `400`). Measured on CI at `53e2687`: **16 checks** on each of the ten legs (QuestAccept, Interact, QuestTurnIn, Equipment, CombatV2, AlphaProfile, DeathReturn, CombatDamage, MobBehavior, DeathReturnAlpha), and with the `AlphaLoot` legs added, measured locally at this head: eleven legs at 16 checks plus the refusal leg at 3. `P1:AlphaLoot` is the tenth production switch and it needs a different kind of leg, because alone it is not a bootable configuration at all - `AlphaLootPolicy.Validate` refuses (`the mob coin band exists only in DESIGN-BM-ALPHA-20261103`), so `gate-refusal` boots it, requires that nothing ever answers `/health`, and asserts the startup log names the missing partner. `AlphaLootAlpha` then proves the other half: with the profile on and the grant flag on, the route surface is still exactly AlphaProfile's, so a payout switch cannot add an endpoint. `DeathReturnFixture` is the second refusal leg: `P1:DeathReturn:RestoreHpFixture=5` under `P1:AlphaProfile` must not start either, because DEC-DEATH-RETURN-20261105 fixes the returned HP by formula and a fixture would silently override it - the same class of bug the profile exists to catch, one config keystroke away.

- `restart` (work order 29 Q8: "Phải có restart HTTP proof trước khi gọi Health durable") is one job with **two server processes on one port**: the runner boots process #1 with the dev gate set, drives the whole `P00-01` loop in it (accept → three package claims → turn-in paying 20 COIN + the `EQ-MK-CHEST-T1-R-COMMON` chest → equip to `CHEST`, ending at quest revision 6 / inventory revision 2), writes what it proved to an evidence file, **stops the PID it owns and waits for the port to stop answering**, boots process #2 on the same port and hands it the file. Process #2 must then show: the old session ids unknown on both reads *and* on a write carrying the old `X-Session-ID` header (`404 session_not_found`), the same character reading exactly as a cold account (`P00-01 AVAILABLE` revision 1 with counter 0, the other four `LOCKED`, inventory revision 0 with no items and no currencies), and the recorded idempotency keys no longer replaying stored receipts — the equip key is refused `409 revision_conflict` (measured: `Equipment.cs` compares the snapshot revision before it looks the instance up, and `P1Validation` refuses `expectedRevision < 1`, so a cold store at revision 0 cannot even be named by a recorded payload), the turn-in key is refused `409 invalid_transition` once the actor is standing at the turn-in NPC (measured from the spawn point it is `422 out_of_range` first, so the profile walks there) and pays no second reward, which the run asserts by re-reading the cold inventory. Finally the loop is re-run cold and lands on the same numbers (accept → revision 2, package claim → counter 1 at revision 3), so "nothing survived" is not confused with "the server is broken". **The durability finding this proves rather than argues:** after a restart the replayed key is re-evaluated, and what stops the 20 COIN + chest from being paid twice is the *quest-state guard*, not the idempotency ledger — a durable store has to persist both, or a replay against surviving state would re-grant. Measured on CI at `44a86fa`: `restart-before` **42 checks**, `restart-after` **24 checks**, ending `E2E PASS (profile=restart pid1=2522 pid2=2558)` — and the same two numbers twice in a row locally against two successive processes. One limit worth stating: process identity is taken from the owned PID (and, on Windows, from the socket owner resolved out of `netstat`), because `/health` returns `status`/`service`/`correlationId` and carries **no** instance identity — adding one is a wire change, and it is what the `GET /p1/capability` packet proposes rather than something this profile slipped in.

The Bến Mưa topology fixture is `SYNTHETIC_TEST_ONLY`, so wall enforcement is `not_enforced` on the dev server: the wall-crossing move succeeds and the scenario records `wall_enforcement=not_enforced`. When a `REVIEWED` bundle lands, the same move must return `422 movement_blocked`; the scenario accepts exactly those two outcomes and fails on anything else. The wall/sweep logic itself is verified deterministically by the self-check's reviewed synthetic bundle. `server-e2e` runs seven whole-loop profiles in CI, the `gate-one` profile as a thirteen-leg matrix (eleven route legs plus two refusal legs: `AlphaLoot`, `DeathReturnFixture`) and the two-process `restart` proof — twenty-one jobs, each with its own port; only the restart job puts two successive processes on one of them.

## Private-alpha launcher on Windows (QOD-24 Q8)

`Server/Health/Smoke/launch_alpha.ps1` starts the server for a person (or a client) rather than for a test run, and it owns exactly one PID:

```powershell
# start: alpha gate set on port 5081 (or -GateSet dev for the four gameplay gates)
powershell -NoProfile -ExecutionPolicy Bypass -File Server\Health\Smoke\launch_alpha.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File Server\Health\Smoke\launch_alpha.ps1 -Port 5082 -GateSet dev -Build

# ask what is running: owned PID alive? + what /health says
powershell -NoProfile -ExecutionPolicy Bypass -File Server\Health\Smoke\launch_alpha.ps1 -Status -Port 5081

# stop only the process this launcher started
powershell -NoProfile -ExecutionPolicy Bypass -File Server\Health\Smoke\launch_alpha.ps1 -Stop -Port 5081
```

- The gates are set as **environment variables for the child process only**; `appsettings.json` is never touched, so every `P1:*` switch stays `false` in the release configuration. `-GateSet alpha` turns on the nine gates the private-alpha loop touches plus `P1:DeathReturn` — the e2e `alpha-p00` profile deliberately leaves `DeathReturn` off, but a client testing the death loop needs the route, and the route is mapped only when `AlphaProfile` **and** `DeathReturn` are both on. It also raises the starting pools to 2000/500, which is endurance for a demo, not balance.
- **Health identity:** `/health` answers `status`/`service`/`correlationId` and carries no instance or build field, so identity here is the owned PID plus the recorded binary path and its write timestamp. Publishing a real instance identity is a wire change and belongs to the `GET /p1/capability` packet, not to a launcher.
- **Stop owned PID:** the start writes `{Id, StartTime, Binary, BinaryWritten, Port, GateSet, Gates}` to `%TEMP%\p1-alpha-<port>.pid`; `-Stop` re-reads it, compares the live process's start time with the recorded one and **refuses to kill on a mismatch** (a recycled PID belongs to somebody else), then verifies the port stops answering and prints `port_released=OK`. Starting on a port that already answers is refused for the same reason: the launcher never stops what it did not start.
- Verified on this machine at this head: `-GateSet dev` on 5095 and 5096 (healthy in 2 s), `-Status` reporting `alive=True` plus the live `/health` fields, a second start on a busy port refused, and `-Stop` releasing both ports (`port_released=OK`, no listener left in `netstat`). One caveat for automation: the server inherits the launcher's output handle, so piping the launcher's own output (`... | tail`) stays open until the server exits — redirect to a file or run it in a terminal.

## Current limits

- Sessions are in memory and lost on restart; there is no database, authentication or real-time transport. The loss is no longer only a claim: the `restart` profile boots a second process on the same port and shows over HTTP which state disappeared (sessions, quest progress, currency, items, the equipped slot and every idempotency ledger), so the durable-store proposal starts from a measured baseline instead of an assumption.
- v1 `entities` stays empty (frozen contract); the v2 opt-in snapshot (`P1:CombatV2`) returns the AOI entity read model and the tick engine applies basic/MK03 damage, death and respawn, the DEC-022 guard window with its confirmation, whiff and next-tick counter, and mob AI impacts. Loot rolls stay dry-run receipts until **both** `P1:AlphaProfile` and `P1:AlphaLoot:GrantEnabled` are on (`alpha-p00` proves a paid kill over HTTP: the sourced coin band, exactly one mutation per death); XP is `applied: false` on every profile that does not name the rule, and `applied: true` only under `P1:AlphaProfile`, which supplies the 25%/55% accept-snapshot formula. Group-clear spawn composition beyond the timer is still missing. The QOD-16 phase-1 domain (damage formula, seeded RNG, mob-stat bundle, internal entity projection) is applied by the tick engine and by mob attacks, both behind the `P1:CombatDamage` gate.
- Dash outcomes (landed position, achieved distance and `COMPLETE`/`BLOCKED_BY_GEOMETRY`/`ZERO_DISTANCE`) live in `DashLedger`, a bounded 512-entry audit keyed by castId. They are **not** on the wire: `CombatEventV2` has no movement type and `WorldSnapshotV2.self` has no stop reason, and the design resolution forbids stuffing fields into `additionalProperties=false` schemas, so the ledger plus the position/revision change in the snapshot is what P1 proves today. The Content Bible row for Tầm Long also lists 150% damage on the first target and +1 Kiếm Ý; with no dash hit-shape field in any canonical content (design resolution §4) and no resource rule approved for it, the dash deals no damage and grants no resource — both recorded as open cases rather than implemented off a narrative table.
- A mob's committed swing has an authoritative **read model** too, and it is also not on the wire: `MobTelegraphProjection.Project(entities)` reports only engaged entities with `state`, the `targetCharacterId` the AI is swinging at, `impactInTicks` / `recoverInTicks` / `nextAttackInTicks` counted down against the server clock in 20 Hz ticks, the absolute `impactAtUtc` for clients that pair it with `serverTimeUtc`, and the mob's `rangeWu`. Timing is computed with integer ceiling on 100 ns ticks because the windows are exact multiples like 0,45 s, and double arithmetic on `TotalSeconds` turns that into 9,0000000000000002. `angleDegrees` is deliberately `null`: no canonical content exports a per-move telegraph shape (width/length/arc), and the defender-side 120° from DEC-022 describes the *guard*, not the swing, so borrowing it would be a fabricated number. What a client can do with it once published: start a warning ring on `TELEGRAPH`, time the lean-back on `impactInTicks`, and know that a swing stays committed even after the target steps out of reach (the impact frame still happens; only the damage check knows it will whiff). The contract ask — an optional versioned `telegraph` block on the v2 snapshot's entities — is in `Implementation/Work_Orders/Proposals/QOD-16_WorldProjectionCombatSubset_vi.md` §9.15 and **not** applied.
- Combat status has an authoritative **read model** but no wire field yet: `CombatStatusProjection.Project(session, tick, now)` answers guard `NONE`/`GUARD`/`WHIFF`/`EXPIRED` with the owning `guardCastId` and window end ticks, whether a counter is still reserved and how it resolved, the actor's HP/MP/Kiếm Ý, the action keys still inside cooldown, and the last dash outcome (achieved vs requested WU, stop reason, landing point). That is what a reconnecting client would need instead of replaying events that already left the bounded buffer. Publishing it means an optional versioned `combat` object on `WorldSnapshotV2` plus a capability flag — drafted in `Implementation/Work_Orders/Proposals/QOD-16_WorldProjectionCombatSubset_vi.md` §9.12 and **not** applied, because both v1 and v2 forbid fields nobody approved.
- Returning from a downed state is a server-owned policy, and since DEC-DEATH-RETURN-20261105 it also has a route: `POST /p1/actor/death-return` (mapped only with `P1:AlphaProfile` **and** `P1:DeathReturn` on). `DeathReturnService.ReturnToAnchor(sessionId, idempotencyKey)` takes no coordinates at all — the payload is `{}` and an unmapped member is refused before the domain is reached — so a client-chosen revive point is not merely rejected, it is unrepresentable. What the decision fixed, in order: the actor must be downed (`409 not_downed` for a fresh key while alive), the map must have bounds **and** be the anchor's own map (`409 unknown_map`, because a cross-map return would be the generic client teleport every source forbids), HP comes back as `max(1, ceil(currentEffectiveMaxHp * 0.5))` where `currentEffectiveMaxHp` is `actor.MaxHp` (equipment is still metadata-only, so there is no bigger formula to approximate), MP is **not** restored, only clamped to its own maximum, and the three penalties are echoed as zero with `const 0` in the schema so a future penalty needs a new decision. A committed return starts a cooldown of `newDeathReturnCooldownSeconds` (three seconds = 60 ticks at 20 Hz) measured from the apply tick; a refusal or a replay never extends it, and `nextReturnAllowedAtTick` travels in the result always and in the error for `422 death_return_cooldown`, so a client schedules its retry from the server's tick. Replay is ordered ahead of both state guards and returns the **same committed snapshot verbatim** — including its `serverTick` and `revision`, with `applied: false`/`replayed: true` — which is why the decision tells consumers to fresh-read the world instead of treating a receipt as current state. The receipt also answers a specific death: `PlayerLifeLedger` records every positive-to-zero transition inside the same actor lock and revision as the damage commit (mob attack, boss encounter, training wave), derives `deathEventId` as `PDEATH_` + lowercase SHA-256 over the canonical JSON array `[characterId, lifeVersion, deathRevision]` rather than minting an id, advances `lifeVersion` exactly once per committed zero-to-positive resurrection, and is keyed by character so it survives a reconnect. Nothing was added to `CombatEventV2` or to the frozen world snapshot: the downed state stays authoritative `hp <= 0`, which is what the client renders. It applies only to a downed actor on a map with known bounds, moves it to the server's own anchor (`P1World:SpawnX/SpawnY` clamped into that map's bounds — a labelled DEV fixture, because canonical content has no per-map `safe_anchor` field and map bounds say nothing about walkability), bumps the actor revision once, and cleans the previous life up as events: the guard window closes as `DEFENDER_DOWN` (reduction stops, whiff reward lost, Kiếm Ý zeroed per DEC-022 §3), every in-flight cast emits `CANCEL` + `END` exactly once with no damage and no kill credit, and a counter reserved for a later tick is cancelled with `CounterOutcome=RETURNED_TO_ANCHOR` instead of being left to swing. Mob aggro needs no separate ledger: `MobLifecycleService.FindTarget` re-runs each tick and skips a player at `Hp <= 0`, so a mob mid-telegraph drops the pending impact. Idempotency is keyed by request in a bounded 256-entry ledger — a repeated key replays the recorded answer (no second move, no second revision, no extra events), a key already used by another character is refused with `idempotency_key_conflict`, refusals are never recorded so the same key stays usable for the retry, and four threads on one key produce exactly one return. Nothing is restored unless `P1:DeathReturn:RestoreHpFixture` is configured (default `0` = the return relocates and clears state but leaves HP alone), and **no penalty is applied**: Production_Rules has no XP/durability/currency/death-timer value to transcribe. `P1:DeathReturn:Enabled` stays `false` and the endpoint contract, the missing anchor/restore/penalty/transition sources and the overlap with the unrouted `ITeleportService` `DEATH_RETURN` reason (which asks the client for `mapId/xWu/yWu`, i.e. exactly the thing this policy refuses) are filed in proposal §9.13.
- Mob behaviour (`MobLifecycleService`) exists as a tickable state machine (IDLE/AGGRO/CHASE/TELEGRAPH/ATTACK/RECOVER/RETURN/DEAD, the Art Bible §6 bestiary cycle) with LOS, leash, attack-range, telegraph and cooldown gates, driven by the 20 Hz `WorldTickBackgroundService` when `P1:MobBehavior:Enabled=true` (off by default). TELEGRAPH holds for `TelegraphSeconds`, then the same tick emits the ATTACK impact frame and settles into RECOVER; losing the target or crossing the leash cancels a pending impact. `MobAttackService` turns an impact frame into player damage only when `P1:CombatDamage:Enabled=true`: it uses the archetype's basic move (the "Đòn thường" column of Art Bible §12) against the completion_v1 player armor baseline and re-checks range, floor and alive state at impact, so outrunning the telegraph whiffs. Every radius, speed, telegraph and recovery duration is a labelled DEV fixture, mob impacts never roll hit or crit (no mob accuracy/crit source exists), and there is no mob loot on death yet. A mob impact is also the DEC-022 trigger: while the defender holds a guard window the damage is reduced by 0.70 from the front (0.20 during the whiff buff) and the first valid front hit reserves the counter. Teleport has no endpoint.
- The Bến Mưa world-entity registry (`world_entities_bm.json`: 44 spawned entities (25 mob members across 8 manifest groups, 2 bosses, 8 NPCs, 5 nodes, 4 interactables), 22 templates) is loaded with despawn/respawn state; interact uses it for shared `INTERACTABLE` claims and per-character (`claimPolicy: PER_CHARACTER`) package claims, and combat resolves alive mobs/bosses by instance ID. The 352-entry world record catalog (`world_records.json`) maps entities to `recordId`s for interact claims and quest progress.
- On **v1**, a cast still carries no damage, hit chance, telegraph, death or loot: `combat.effect` records an accepted cast and its cooldown, and that is the frozen contract. Those results travel on the gated **v2** surface instead - `POST /p1/v2/combat` plus the event stream (`IMPACT`/`MISS`/`COUNTER_CONFIRMED`/`DEATH`) and the v2 snapshot's health fields - so the claim is about which vocabulary a client reads, not about the engine being absent. The canonical damage formula and mob stats are gated domain (see the QOD-16 section) and stay behind `P1:CombatDamage`.
